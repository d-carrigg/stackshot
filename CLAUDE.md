# stackshot

Multi-panel image composer for code/screenshots/images. CLI is `stackshot`.
Package code lives in `src/cli/` (imported as `stackshot`), tests in `tests/`,
built and managed with `uv`.

## Release flow

All changes ship through feature branches. Never commit directly to `main`.

1. **Branch.** Cut a feature branch from `main`:
   `git checkout -b <topic>` (e.g. `fix-arrow-aa`, `add-vertical-layout`).
2. **Code + test.** Make the change. Add/update tests under `tests/`. Run
   `uv run pytest` locally.
3. **Bump the version** in `pyproject.toml` (`[project].version`) as part
   of the same PR. Use semver:
   - patch (`0.2.1 → 0.2.2`) for bug fixes,
   - minor (`0.2.x → 0.3.0`) for new features,
   - major (`0.x.y → 1.0.0`) for breaking changes.
   Every PR that ships user-visible change must bump the version. If
   there's no user-visible change (pure refactor, CI tweak, docs), no bump.
   Also set the same version in `.claude-plugin/plugin.json` and in the
   plugin entry of `.claude-plugin/marketplace.json`
   (`tests/test_plugin.py` fails if they drift).
4. **Update `CHANGELOG.md`** with a new section for the bumped version
   (Fixed / Changed / Added). Follow the existing format.
5. **Open a PR to `main`.** CI (`test.yml`) runs pytest on 3.11 and 3.13.
6. **Merge.** On push to `main`, `release.yml` reads the version from
   `pyproject.toml`, pushes a `v<version>` tag if it doesn't exist, and
   then builds standalone binaries for Linux/macOS/Windows + attaches
   them (with the license bundles) to the GitHub Release.

If you forget to bump the version, the tag-version job is a no-op (tag
already exists) and binaries aren't rebuilt. Bump and merge again to ship.

## Workflows

- `.github/workflows/test.yml` — pytest on push/PR.
- `.github/workflows/release.yml` — on push to `main`: tags
  `v<version>` if new, then builds + uploads binaries. Single workflow
  because GitHub Actions suppresses workflow triggers from
  `GITHUB_TOKEN`-pushed tags; chaining via a separate "on tag push"
  workflow silently never ran (PyPI publish is gated; see comment in the file).
- `.github/workflows/deploy-web.yml` — deploys the web app to SWA on
  push to main.

## Local commands

- `uv sync --group dev` — install deps including pytest.
- `uv run pytest` — full test suite (must stay fast and real; no subprocess
  shelling, no mocks of the package under test).
- `uv run stackshot <panels>` — run the CLI from the working tree.
- `uv build` — build sdist + wheel into `dist/`.

## Project layout

- `src/cli/` — CLI package source, imported as `stackshot` (see `[tool.setuptools]`
  in `pyproject.toml` mapping `stackshot` → `src/cli`). The web app lives in `src/web/`.
- `tests/` — pytest tests. Call entry points in-process; don't shell out.
- `docs/img/` — sample images embedded in the README. Regenerated by
  `tests/test_samples.py` — running the suite refreshes them in place.
- `docs/examples/` — source files used as panel inputs in samples
  (e.g. `print_loop.py`). When adding a sample, prefer a real file
  here over inline strings in `test_samples.py`. Recording scripts
  for animated samples live here too — e.g. `record_print_loop.sh`
  regenerates `docs/img/print_loop.gif` via asciinema + agg. The
  intermediate `*.cast` files are gitignored — re-run the script to
  regenerate them.
- `CHANGELOG.md` — keep in lockstep with version bumps.
- `.claude-plugin/` + `skills/stackshot/SKILL.md` — the repo doubles as a
  Claude Code plugin and marketplace. The skill runs the CLI via
  `uv run --project "${CLAUDE_PLUGIN_ROOT}"`; keep its flag list in sync
  with `cli.py` (`tests/test_plugin.py` checks it). Validate with
  `claude plugin validate .`.

## Conventions

- Python ≥ 3.11. Use `tomllib` (stdlib) for TOML, no `toml`/`tomli` deps.
- Don't add inline-shell verification (`printf | … && sleep && ls`). Write
  a pytest test instead.
- Keep tests fast and real — exercise the actual contracts, not helpers,
  and don't spawn subprocesses for what can be called in-process.

## Third-party attribution

stackshot is MIT-licensed and ships two attribution bundles. Both are
markdown files at the repo root and both are surfaced inside the web
app's "Open-source licenses" modal:

- `THIRD_PARTY_LICENSES.md` — Python packages and native libraries
  bundled in the standalone binaries published to GitHub Releases.
  Hand-maintained; edit when a CLI dep is added/removed/upgraded.
- `THIRD_PARTY_LICENSES_WEB.md` — npm packages bundled in the web
  build under `src/web/dist`. Generated by
  `src/web/scripts/generate-web-licenses.mjs` from the current
  production dep tree (`npm ls --omit=dev --all --json`).

When you change web dependencies in `src/web/package.json` or
`package-lock.json`, regenerate the web file:

```bash
cd src/web && node scripts/generate-web-licenses.mjs
```

Commit the updated `THIRD_PARTY_LICENSES_WEB.md` in the same PR as
the dep change. Both files are imported via Vite `?raw` at build
time, so failing to commit the regenerated file ships stale
attribution to users.

When adding a CLI dependency, update `THIRD_PARTY_LICENSES.md` by
hand. Each entry should include: package name + version, license
identifier, project URL, and the verbatim license text (copied from
the upstream `LICENSE` file). The Summary table at the top of the
file lists every package — keep that in sync too. Attribution is a
real obligation, not a formality; missing entries are a release
blocker.
